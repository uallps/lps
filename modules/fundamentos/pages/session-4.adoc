== ¿Qué es SwiftCrossUI?

*SwiftCrossUI* es un framework para crear interfaces gráficas con una sintaxis *parecida a SwiftUI*, pero que funciona en varias plataformas. Es un proyecto de código abierto (https://github.com/moreSwift/swift-cross-ui[moreSwift/swift-cross-ui]) y no pertenece a Apple.

* Se escribe en Swift con vistas declarativas (`VStack`, `Text`, `Button`, `ForEach`…), `@State` y `@main struct ... : App`.
* No dibuja los controles por su cuenta: usa un *backend* nativo de cada plataforma. En macOS, *AppKit*; en Linux, *GTK4*; también existen backends para iOS (UIKit) y Windows (WinUI).
* Desde la versión *0.10.0* admite la macro `@Observable`, así que el mismo ViewModel de la sesión 3 sirve en SwiftUI y en SwiftCrossUI.

[cols="1,2,2",options="header"]
|===
| | SwiftUI | SwiftCrossUI

| Quién lo mantiene
| Apple
| Comunidad (moreSwift)

| Plataformas
| macOS, iOS, tvOS, watchOS, visionOS
| macOS, Linux, Windows (según el backend) e iOS

| Cómo se obtiene
| Viene con Xcode
| Dependencia de Swift Package Manager

| API
| Muy amplia
| Parecida, pero *no idéntica* y más reducida
|===

[NOTE]
====
SwiftCrossUI no intenta replicar SwiftUI al detalle. Puede haber controles o modificadores que existan en uno y no en el otro, y como es una versión `0.x`, su API todavía puede cambiar entre versiones. Por eso fijamos la versión *0.10.0*.
====

== Instalar SwiftCrossUI con Swift Package Manager

SwiftCrossUI no se instala en el sistema: se declara como *dependencia* en el `Package.swift` del proyecto y Swift Package Manager (SwiftPM) la descarga y la compila.

=== Requisitos

* *macOS:* Xcode o las herramientas de Swift 6.1 o superior. No hace falta instalar nada más: se usa el backend AppKit.
* *Linux:* Swift 6.1 o superior y las librerías de desarrollo de GTK4.

[source,shell]
----
sudo apt-get update
sudo apt-get install -y clang pkg-config libgtk-4-dev
----

=== Declarar la dependencia

Se añade el paquete en `dependencies` y los dos productos que necesitamos en el target ejecutable:

[source,swift]
----
// swift-tools-version: 6.1
import PackageDescription

let package = Package(
    name: "TaskApp",
    platforms: [.macOS(.v14), .iOS(.v17)],
    products: [
        .executable(name: "TaskApp", targets: ["TaskApp"]),
    ],
    dependencies: [
        .package(
            url: "https://github.com/moreSwift/swift-cross-ui.git",
            .upToNextMinor(from: "0.10.0")
        ),
    ],
    targets: [
        .executableTarget(
            name: "TaskApp",
            dependencies: [
                .product(name: "SwiftCrossUI", package: "swift-cross-ui"),
                .product(name: "DefaultBackend", package: "swift-cross-ui"),
            ]
        ),
    ]
)
----

* `.package(url:…)` indica *de dónde* se descarga y qué versiones se aceptan. `.upToNextMinor(from: "0.10.0")` admite 0.10.x pero no 0.11, que podría romper la API.
* `SwiftCrossUI` es el framework de vistas y `DefaultBackend` elige el backend adecuado a la plataforma (AppKit en macOS, GTK4 en Linux).
* La primera compilación descarga y compila el paquete y tarda varios minutos. SwiftPM anota la versión resuelta en `Package.resolved`; hay que subir ese fichero al repositorio.

[IMPORTANT]
====
*Trabajad con un paquete, no con un proyecto de Xcode.* Si creáis un proyecto de aplicación con Xcode (`.xcodeproj`) y después compiláis con `swift run` en la carpeta del proyecto, SwiftPM crea una carpeta `.build` con las dependencias descargadas dentro del proyecto. Xcode la recoge y deja de resolver el proyecto con el error:

`multiple packages ('package-benchmark', 'swift-benchmark') declare targets with a conflicting name: 'Benchmark'`

SwiftCrossUI 0.10.0 y una de sus dependencias declaran un target con ese mismo nombre. SwiftPM lo tolera y Xcode, cuando ve esas carpetas dentro del proyecto, no.

* Cread el proyecto con `swift package init --type executable` y *sin* `.xcodeproj`. Si queréis usar Xcode, abrid directamente la carpeta del paquete o su `Package.swift`.
* Si ya os ha pasado, borrad la carpeta `.build` del proyecto y volved a abrirlo.
* Añadid `.build/` al `.gitignore`.
====

=== Primera ventana con SwiftCrossUI

[source,swift]
----
import SwiftCrossUI
import DefaultBackend

@main
struct TaskApp: App {
    var body: some Scene {
        WindowGroup("TaskApp") {
            Text("Hola desde SwiftCrossUI")
                .padding()
        }
    }
}
----

[source,shell]
----
swift run
----

Si se abre una ventana con el texto, la instalación es correcta. Sobre `TaskApp` el código es casi igual que con SwiftUI: cambian los `import`, y el resto de la vista es el mismo.

== Un proyecto, varios productos

Queremos que el código de la aplicación no cambie y que solo cambie el *framework* con el que se compila. Para ello separamos el proyecto en tres módulos.

[plantuml]
----
@startuml
skinparam monochrome true
skinparam shadowing false
skinparam roundCorner 5
left to right direction

rectangle "TaskApp\n(ejecutable)" as App
rectangle "TaskUI\n(fachada de interfaz)" as UI
rectangle "TaskCore\n(modelo y ViewModel)" as Core
rectangle "SwiftUI" as SUI
rectangle "SwiftCrossUI +\nDefaultBackend" as SCUI

App --> UI
App --> Core
UI ..> SUI : trait SwiftUI
UI ..> SCUI : trait SwiftCrossUI
@enduml
----

[listing]
----
TaskApp/
├── 📄 Package.swift
└── 📁 Sources/
    ├── 📁 TaskCore/
    │   └── 📄 ...                  // Model y ViewModel: Swift puro, sin interfaz
    ├── 📁 TaskUI/
    │   └── 📄 TaskUI.swift         // Reexporta el framework de interfaz elegido
    └── 📁 TaskApp/
        └── 📄 TaskApp.swift        // @main y vistas
----

* *TaskCore:* el *Model* y el *ViewModel* de la sesión 3. No importa ningún framework de interfaz, solo `Foundation` y `Observation`.
* *TaskUI:* un módulo casi vacío que decide qué framework de interfaz recibe la aplicación.
* *TaskApp:* el ejecutable con el `@main` y las vistas. Solo importa `TaskUI` y `TaskCore`.

=== Los productos con traits

Un *trait* es una opción que se activa al compilar el paquete (SwiftPM 6.1 o superior). Cada trait que declaramos es una variante del producto:

[source,swift]
----
// swift-tools-version: 6.1
import PackageDescription

let package = Package(
    name: "TaskApp",
    platforms: [.macOS(.v14), .iOS(.v17)],
    products: [
        .executable(name: "TaskApp", targets: ["TaskApp"]),
    ],
    traits: [
        .trait(name: "SwiftUI", description: "Producto con SwiftUI (solo Apple)"),
        .trait(name: "SwiftCrossUI", description: "Producto con SwiftCrossUI"),
        .default(enabledTraits: ["SwiftUI"]),
    ],
    dependencies: [
        .package(
            url: "https://github.com/moreSwift/swift-cross-ui.git",
            .upToNextMinor(from: "0.10.0")
        ),
    ],
    targets: [
        .target(name: "TaskCore"),
        .target(
            name: "TaskUI",
            dependencies: [
                .product(
                    name: "SwiftCrossUI",
                    package: "swift-cross-ui",
                    condition: .when(traits: ["SwiftCrossUI"])
                ),
                .product(
                    name: "DefaultBackend",
                    package: "swift-cross-ui",
                    condition: .when(traits: ["SwiftCrossUI"])
                ),
            ]
        ),
        .executableTarget(
            name: "TaskApp",
            dependencies: ["TaskCore", "TaskUI"]
        ),
    ]
)
----

* `traits:` declara las variantes. `.default(enabledTraits:)` indica cuál se usa si no se elige ninguna.
* `condition: .when(traits: [...])` hace que SwiftCrossUI solo se *descargue y compile* cuando el trait `SwiftCrossUI` está activo.
* Dentro del código del paquete, cada trait activo es una condición de compilación con su nombre: `#if SwiftCrossUI`.

[source,shell]
----
swift run                           # producto SwiftUI (por defecto)
swift run --traits SwiftCrossUI     # producto SwiftCrossUI
----

[IMPORTANT]
====
Los traits son *aditivos*: SwiftPM no impide activar `SwiftUI` y `SwiftCrossUI` a la vez. En `TaskUI` se resuelve poniendo `SwiftCrossUI` primero en el `#if`, y SwiftUI solo existe en plataformas Apple. Para elegir el producto usad siempre `--traits` en la terminal.
====

=== El módulo TaskUI con `@_exported`

`TaskUI` contiene un único fichero. `@_exported import` hace que quien importe `TaskUI` reciba también el framework reexportado, como si lo hubiera importado directamente:

[source,swift]
----
#if SwiftCrossUI
@_exported import SwiftCrossUI
@_exported import DefaultBackend
#elseif SwiftUI
@_exported import SwiftUI
#else
#error("Activa un trait de interfaz: SwiftUI o SwiftCrossUI")
#endif
----

Así, en la aplicación basta con `import TaskUI`:

[source,swift]
----
import TaskUI
import TaskCore

@main
struct TaskApp: App {
    var body: some Scene {
        WindowGroup("TaskApp") {
            TaskListView()
        }
    }
}

struct TaskListView: View {
    @State var viewModel = TaskListViewModel()

    var body: some View {
        VStack {
            ForEach(viewModel.tasks) { task in
                HStack {
                    Button(task.isCompleted ? "✓" : "○") {
                        viewModel.toggleCompletion(id: task.id)
                    }
                    Text(task.title)
                }
            }
            Button("Añadir tarea") {
                viewModel.addTask()
            }
        }
        .padding()
    }
}
----

El *mismo fichero* se compila con SwiftUI o con SwiftCrossUI, según el trait. El ViewModel es el `@Observable` de `TaskCore`, el de la sesión 3, sin cambios.

[NOTE]
====
`@_exported` es un atributo con guion bajo: funciona y se usa mucho, pero no es parte estable del lenguaje. Por eso lo aislamos en un único fichero.
====

== Cuando SwiftCrossUI no soporta algo: una vista por versión

Compartir el código tiene un límite: solo vale para lo que *existe en los dos frameworks con la misma forma*. Partimos de la fila de tarea del curso anterior, escrita para SwiftUI:

[source,swift]
----
HStack {
    Button(action: toggleCompletion) {
        Image(systemName: task.isCompleted ? "checkmark.circle.fill" : "circle")
    }
    .buttonStyle(.plain)
    VStack(alignment: .leading) {
        Text(task.title)
            .strikethrough(task.isCompleted)
        if let dueDate = task.dueDate {
            Text("Vence: \(dueDate.formatted(date: .abbreviated, time: .shortened))")
                .font(.caption)
                .foregroundColor(.secondary)
        }
    }
}
----

Este código *no compila* con SwiftCrossUI 0.10.0:

[cols="1,2",options="header"]
|===
| En SwiftUI | En SwiftCrossUI

| `Image(systemName:)`
| No existe: `Image` solo se crea desde una URL o desde datos de imagen.

| `.strikethrough(_:)`
| No existe.

| `Color.secondary`
| No existe. Sí hay `Color.gray`, `.green`, `.yellow` y `.red`.

| `.font(.caption)`
| Existe y se escribe igual.

| `.foregroundColor(_:)`, `.italic()`
| Existen y se escriben igual.
|===

La regla del proyecto es *no separar versiones con `#if` dentro de las vistas*. Cuando algo no se soporta, se escribe *una vista en cada carpeta de vistas*, con el mismo nombre y *la misma API pública*. La lógica (modelo, ViewModel, flags) se escribe una sola vez en `TaskCore`.

[listing]
----
TaskApp/
├── 📄 Package.swift
└── 📁 Sources/
    ├── 📁 TaskCore/               // Model, ViewModel y AppConfig: Swift puro
    ├── 📁 TaskViewsSwiftUI/       // Vistas de la versión SwiftUI
    │   └── 📄 TaskRowView.swift
    ├── 📁 TaskViewsSwiftCrossUI/  // Vistas de la versión SwiftCrossUI
    │   └── 📄 TaskRowView.swift
    ├── 📁 TaskUI/                 // Fachada: reexporta el framework y las vistas de la versión
    └── 📁 TaskApp/                // @main y vistas comunes
----

*Versión SwiftUI* (`TaskViewsSwiftUI/TaskRowView.swift`), con el código del curso anterior:

[source,swift]
----
import SwiftUI
import TaskCore

public struct TaskRowView: View {
    let task: Task
    let toggleCompletion: () -> Void

    public init(task: Task, toggleCompletion: @escaping () -> Void) {
        self.task = task
        self.toggleCompletion = toggleCompletion
    }

    public var body: some View {
        HStack {
            Button(action: toggleCompletion) {
                Image(systemName: task.isCompleted ? "checkmark.circle.fill" : "circle")
            }
            .buttonStyle(.plain)
            VStack(alignment: .leading) {
                Text(task.title)
                    .strikethrough(task.isCompleted)
                if let dueDate = task.dueDate {
                    Text("Vence: \(dueDate.formatted(date: .abbreviated, time: .shortened))")
                        .font(.caption)
                        .foregroundColor(.secondary)
                }
                if let priority = task.priority {
                    Text("Prioridad: \(priority.rawValue)")
                        .font(.caption)
                        .foregroundColor(priorityColor(for: priority))
                }
            }
        }
    }

    private func priorityColor(for priority: Priority) -> Color {
        switch priority {
        case .low: return .green
        case .medium: return .yellow
        case .high: return .red
        }
    }
}
----

*Versión SwiftCrossUI* (`TaskViewsSwiftCrossUI/TaskRowView.swift`), con lo que sí existe:

[source,swift]
----
import Foundation
import SwiftCrossUI
import TaskCore

public struct TaskRowView: View {
    let task: Task
    let toggleCompletion: () -> Void

    public init(task: Task, toggleCompletion: @escaping () -> Void) {
        self.task = task
        self.toggleCompletion = toggleCompletion
    }

    public var body: some View {
        HStack {
            // sin Image(systemName:): un carácter en un botón
            Button(task.isCompleted ? "●" : "○") {
                toggleCompletion()
            }
            VStack(alignment: .leading) {
                // sin .strikethrough: gris y cursiva
                if task.isCompleted {
                    Text(task.title)
                        .foregroundColor(.gray)
                        .italic()
                } else {
                    Text(task.title)
                }
                if let dueDate = task.dueDate {
                    Text("Vence: \(dueDate.formatted(date: .abbreviated, time: .shortened))")
                        .font(.caption)
                        .foregroundColor(.gray)   // sin Color.secondary
                }
                if let priority = task.priority {
                    Text("Prioridad: \(priority.rawValue)")
                        .font(.caption)
                        .foregroundColor(priorityColor(for: priority))
                }
            }
        }
    }

    private func priorityColor(for priority: Priority) -> Color {
        switch priority {
        case .low: return .green
        case .medium: return .yellow
        case .high: return .red
        }
    }
}
----

En `Package.swift` cada carpeta es un target y la fachada solo depende del de su trait:

[source,swift]
----
.target(name: "TaskViewsSwiftUI", dependencies: ["TaskCore"]),
.target(
    name: "TaskViewsSwiftCrossUI",
    dependencies: [
        "TaskCore",
        .product(name: "SwiftCrossUI", package: "swift-cross-ui",
                 condition: .when(traits: ["SwiftCrossUI"])),
        .product(name: "DefaultBackend", package: "swift-cross-ui",
                 condition: .when(traits: ["SwiftCrossUI"])),
    ]
),
.target(
    name: "TaskUI",
    dependencies: [
        .target(name: "TaskViewsSwiftUI", condition: .when(traits: ["SwiftUI"])),
        .target(name: "TaskViewsSwiftCrossUI", condition: .when(traits: ["SwiftCrossUI"])),
        // ... y los productos de SwiftCrossUI condicionados a su trait
    ]
),
----

Y la fachada `TaskUI` reexporta también las vistas de la versión activa. Es el *único* `#if` entre versiones:

[source,swift]
----
#if SwiftCrossUI
@_exported import SwiftCrossUI
@_exported import DefaultBackend
@_exported import TaskViewsSwiftCrossUI
#elseif SwiftUI
@_exported import SwiftUI
@_exported import TaskViewsSwiftUI
#else
#error("Activa un trait de interfaz: SwiftUI o SwiftCrossUI")
#endif
----

Las vistas comunes ya no saben qué versión se compila. Solo llaman a `TaskRowView` y reciben la de la carpeta activa:

[source,swift]
----
ForEach(viewModel.tasks) { task in
    TaskRowView(task: task) {
        viewModel.toggleCompletion(id: task.id)
    }
}
----

[IMPORTANT]
====
Con carpetas de vistas por versión, `swift build` a secas compila *todos* los targets, incluida la carpeta de la otra versión, y falla. Para compilar usad `swift build --product TaskApp`; `swift run` ya compila solo lo necesario.
====

Otras diferencias que conviene conocer: en SwiftCrossUI no hay `NavigationView` (existe `NavigationStack`), `List` exige siempre un `Binding` de selección y no existen `Form` ni `.navigationTitle`. La apariencia depende además del backend (AppKit o GTK4): no se espera igualdad visual.

== Feature flags: variabilidad en ejecución y en compilación

Un *feature flag* es una configuración que determina si una característica está activa en un producto.

[cols="1,3",options="header"]
|===
| Situación | Resultado

| `showDueDates = false`
| TaskApp sigue funcionando, pero no muestra la fecha de vencimiento.

| `showDueDates = true`
| Las tareas con fecha muestran ese dato adicional.

| `enableProgress = false`
| BookApp mantiene su biblioteca sin mostrar la información de páginas.

| `enableProgress = true`
| La variante de BookApp puede mostrar datos de avance para los libros que los tengan.
|===

Hay dos técnicas, y se diferencian en *cuándo se decide*:

[cols="1,2,2",options="header"]
|===
| | Variabilidad en ejecución | Variabilidad en compilación

| Cuándo se decide
| Con la aplicación funcionando.
| Antes de compilar.

| Cómo se escribe
| Un valor observable (`AppConfig`) que la vista consulta con un `if`.
| Una condición de compilación y un `#if`.

| Para cambiarla
| Se cambia el valor; la View se actualiza *sin recompilar*.
| Hay que *recompilar* el producto.

| Qué pasa con el código desactivado
| Sigue dentro del programa.
| No existe en el programa.
|===

=== Feature flags en ejecución: AppConfig

La configuración pertenece a la aplicación, *no* al modelo de datos. Es una clase `@Observable` más, en `TaskCore`:

[source,swift]
----
import Observation

@Observable
public final class AppConfig {
    public var showDueDates = true
    public var showPriorities = true
    public init() {}
}
----

El modelo `Task` es el de la sesión 3, con `dueDate` y `priority` opcionales. La pantalla principal guarda el `AppConfig` en un `@State`, igual que el ViewModel, y ofrece dos botones para cambiar los flags:

[source,swift]
----
struct TaskListView: View {
    @State var viewModel = TaskListViewModel()
    @State var config = AppConfig()

    var body: some View {
        VStack {
            HStack {
                Button("Fechas: \(config.showDueDates ? "Sí" : "No")") {
                    config.showDueDates.toggle()
                }
                Button("Prioridades: \(config.showPriorities ? "Sí" : "No")") {
                    config.showPriorities.toggle()
                }
            }
            ForEach(viewModel.tasks) { task in
                TaskRowView(
                    task: task,
                    showDueDates: config.showDueDates,
                    showPriorities: config.showPriorities,
                    toggleCompletion: { viewModel.toggleCompletion(id: task.id) }
                )
            }
            Button("Añadir tarea") { viewModel.addTask() }
        }
        .padding()
    }
}
----

Las dos filas (la de cada carpeta de vistas) reciben ahora los flags y la acción como *closure*, y siguen sin conocer el ViewModel. En la versión SwiftUI:

[source,swift]
----
public struct TaskRowView: View {
    let task: Task
    let showDueDates: Bool
    let showPriorities: Bool
    let toggleCompletion: () -> Void

    public init(
        task: Task,
        showDueDates: Bool,
        showPriorities: Bool,
        toggleCompletion: @escaping () -> Void
    ) {
        self.task = task
        self.showDueDates = showDueDates
        self.showPriorities = showPriorities
        self.toggleCompletion = toggleCompletion
    }

    public var body: some View {
        // ...
        if showDueDates, let dueDate = task.dueDate {
            // fecha
        }
        if showPriorities, let priority = task.priority {
            // prioridad
        }
    }
}
----

La versión de SwiftCrossUI recibe exactamente los mismos parámetros y tiene las mismas condiciones.

Las condiciones `if showDueDates` y `if showPriorities` son *puntos de variación visibles*. Cambiar un flag muestra u oculta información sin borrar los datos de las tareas.

*Pregunta:* ¿es lo mismo que la fecha sea `nil` a que la feature esté desactivada? No: el primer caso es el dato de una tarea y el segundo la configuración del producto.

=== Variables de compilación

Una *variable de compilación* (_compilation condition_) es un nombre que se activa al compilar. Desde el código se consulta con `#if`; si no está activa, el compilador *no incluye* ese bloque:

[source,swift]
----
#if Prioridades
if showPriorities, let priority = task.priority {
    Text("Prioridad: \(priority.rawValue)")
}
#endif
----

Hay varias formas de definirla:

[cols="2,3,3",options="header"]
|===
| Dónde | Cómo | Ejemplo

| *Trait* del paquete
| Cada trait activo es una variable con su nombre.
| `swift run --traits Prioridades`

| *`Package.swift`*
| `swiftSettings` del target, con `.define`. Se puede limitar a una configuración.
| `.define("Prioridades", .when(configuration: .debug))`

| *Línea de comandos*
| Se pasa la opción `-D` al compilador.
| `swift run -Xswiftc -DPrioridades`

| *Xcode*
| Ajuste *Active Compilation Conditions* del target, por configuración.
| `SWIFT_ACTIVE_COMPILATION_CONDITIONS = DEBUG Prioridades`

| *Automática*
| Swift define `DEBUG` en las compilaciones de depuración de SwiftPM y de Xcode.
| `#if DEBUG`
|===

[NOTE]
====
Todas las formas producen el mismo efecto: la variable llega al `#if`. Las definidas solo para la configuración `debug` (y la propia `DEBUG`) desaparecen al compilar con `swift run -c release`.
====

==== Una característica con trait

Para que `Prioridades` sea una característica que *pueda no existir* en un producto, la declaramos como trait en el `Package.swift`:

[source,swift]
----
traits: [
    .trait(name: "SwiftUI", description: "Producto con SwiftUI (solo Apple)"),
    .trait(name: "SwiftCrossUI", description: "Producto con SwiftCrossUI"),
    .trait(name: "Prioridades", description: "Característica opcional: prioridad de la tarea"),
    .default(enabledTraits: ["SwiftUI"]),
],
----

Ahora un producto se define por la *combinación* de traits:

[source,shell]
----
swift run                                          # SwiftUI, sin prioridades
swift run --traits SwiftUI,Prioridades             # SwiftUI con prioridades
swift run --traits SwiftCrossUI,Prioridades        # SwiftCrossUI con prioridades
----

El `#if Prioridades` está dentro de *cada* fila por versión: selecciona una *característica*, no un framework, y por eso no incumple la regla de no usar `#if` para separar versiones.

[IMPORTANT]
====
`--traits` *reemplaza* a los traits por defecto, no se suma a ellos. Con `swift run --traits Prioridades` el trait `SwiftUI` deja de estar activo y `TaskUI` falla con su `#error`. Hay que listar todos los traits del producto.
====

Así conviven dos niveles de variabilidad: el trait `Prioridades` decide si el código *existe*, y el flag `showPriorities` decide, en una variante que sí lo incluye, si se *muestra*.

=== Schemes en Xcode

Un *scheme* es una configuración guardada de Xcode que define *qué* se construye y se ejecuta y *con qué opciones*: el target, la configuración de compilación (Debug, Release u otra), los argumentos y las variables de entorno. Cada scheme es una forma de lanzar el producto.

Para tener varias variantes en Xcode:

. *Crear configuraciones.* En el proyecto, pestaña *Info*, sección *Configurations*, duplicad *Debug* con el nombre, por ejemplo, `Debug-Prioridades`.
. *Definir la variable.* En *Build Settings* del target, buscad *Active Compilation Conditions* y añadid `Prioridades` solo a la configuración nueva.
. *Crear un scheme* (*Product > Scheme > Manage Schemes*) llamado `TaskApp-Prioridades` y, en *Edit Scheme > Run > Info*, elegid como *Build Configuration* la configuración nueva.

Desde el menú de schemes se elige entonces la variante antes de ejecutar. El equivalente por terminal es:

[source,shell]
----
xcodebuild -scheme TaskApp -destination 'platform=macOS' \
    SWIFT_ACTIVE_COMPILATION_CONDITIONS='$(inherited) Prioridades' build
----

[NOTE]
====
`xcodebuild` no tiene ninguna opción para elegir traits. Por eso en esta sesión *los traits se eligen siempre con `swift run --traits ...`* en la terminal, y los schemes se usan para las variables de compilación.
====
