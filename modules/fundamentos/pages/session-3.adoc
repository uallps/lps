== Teoría: Modelos de Características (Cap. 3 y 4)

Un Modelo de Características es una estructura de árbol que representa todas las características de una Línea de Productos Software (LPS) y las relaciones entre ellas. Es la principal herramienta para definir y gestionar la variabilidad.

=== ¿Qué es una Característica (Feature)?

Una característica es una unidad de funcionalidad visible para el usuario o un stakeholder. Es algo que un producto "hace" o "tiene". Ejemplos: "Guardar en la nube", "Modo oscuro", "Notificaciones push".

=== El Diagrama de Características

Es la representación visual del modelo. Se lee de arriba abajo, descomponiendo características complejas en otras más simples.

.Componentes Principales
- **Raíz (Root):** El nodo superior, que representa el producto o la LPS en su conjunto.
- **Características Hijas:** Descomposición de una característica padre.
- **Relaciones de Variabilidad:** Definen cómo se pueden seleccionar las características hijas.

=== Notación del Diagrama

[cols="1,3"]
|===
| Símbolo | Descripción

| *Característica Obligatoria (Mandatory)*
| Un círculo relleno (`●`). Si se elige el padre, esta característica *debe* ser incluida. Es una relación 1 a 1.

| *Característica Opcional (Optional)*
| Un círculo vacío (`○`). Si se elige el padre, esta característica *puede o no* ser incluida. Es una relación 0 a 1.

| *Grupo Alternativo (Alternative / XOR)*
| Un arco que conecta varias características opcionales. Si se elige el padre, *exactamente una* de las características del grupo debe ser seleccionada.

| *Grupo Opcional Múltiple (Or)*
| Un arco relleno que conecta varias características opcionales. Si se elige el padre, *una o más* de las características del grupo pueden ser seleccionadas.
|===

=== Restricciones Cruzadas (Cross-Tree Constraints)

A veces, la selección de una característica en una rama del árbol afecta a otra en una rama diferente.

- `requires`: La selección de la característica A implica que la característica B también debe ser seleccionada.
- `excludes`: La selección de la característica A impide que la característica B sea seleccionada.

== Arquitectura del proyecto: organizar las piezas con MVVM

Antes de programar, vamos a separar las responsabilidades. Esto permitirá reutilizar el modelo y las operaciones de TaskApp o BookApp aunque cambie el framework de interfaz.

=== Qué significa Model — View — ViewModel

[cols="1,2,2",options="header"]
|===
| Capa | Responsabilidad | Ejemplo de TaskApp

| *Model (M)*
| Datos y reglas del dominio; no conoce los controles de la interfaz.
| `Task`, `Priority`.

| *View (V)*
| Dibuja controles y comunica acciones del usuario; no almacena por sí sola la lógica de negocio.
| `TaskListView`, `TaskRowView`.

| *ViewModel (VM)*
| Contiene el estado de la pantalla, la colección y las operaciones; la View observa sus cambios.
| `TaskListViewModel`.
|===

.Flujo MVVM en TaskApp
[plantuml]
----
@startuml
skinparam monochrome true
skinparam shadowing false
skinparam roundCorner 5
skinparam ArrowFontSize 11
left to right direction

actor "Usuario" as U

package "View (SwiftUI)" as V {
  rectangle "TaskListView\nTaskRowView" as View
}

package "ViewModel" as VM {
  rectangle "TaskListViewModel\n@Observable, tasks" as ViewModel
}

package "Model" as M {
  rectangle "Task\nPriority" as Model
}

U --> View : "1. pulsa «Completar»"
View --> ViewModel : "2. llama a toggleCompletion(task)\n(closure)"
ViewModel --> Model : "3. modifica la tarea"
ViewModel ..> View : "4. el cambio en tasks se notifica;\nla View se redibuja"

note bottom of Model
  El Model no conoce
  ni la View ni el ViewModel
end note
@enduml
----

La View *no* modifica las tareas: delega la acción en el ViewModel. El ViewModel es el único que cambia el Model y avisa del cambio; la View solo muestra el estado actual.

Al final de esta sesión construiremos la primera versión de este flujo con la macro `@Observable` y `@State`, y la sesión 4 lo completará con el resto de operaciones y los feature flags.

== Demostración: traducir las características de TaskApp al modelo Swift

=== Paso 1. El núcleo obligatorio de TaskApp

A partir del diagrama de TaskApp, el Model comienza con el título y el estado de finalización.

[source,swift]
----
import Foundation

struct Task: Identifiable {
    let id = UUID()
    var title: String
    var isCompleted: Bool = false
}
----

`UUID` identifica cada tarea de forma estable. El título es obligatorio, mientras que el estado tiene un valor inicial.

`Identifiable` es un protocolo de Swift que exige una propiedad `id` única y estable. Lo añadimos desde el principio porque la interfaz lo necesitará: `List` y `ForEach` usan ese `id` para saber qué fila es cuál, aunque cambien el título o el estado de la tarea. Por eso el `id` es `let` (la identidad no cambia) y no usamos el título ni la posición en el array.

=== Paso 2. Incorporar datos opcionales

Cuando el modelo necesite también fecha y prioridad, añadimos tipos opcionales:

[source,swift]
----
import Foundation

enum Priority: String, CaseIterable {
    case low = "Baja"
    case medium = "Media"
    case high = "Alta"
}

struct Task: Identifiable {
    let id = UUID()
    var title: String
    var isCompleted: Bool = false
    var dueDate: Date?
    var priority: Priority?
}
----

* `Date?` y `Priority?` permiten que *una tarea concreta* carezca de esos datos.
* El diagrama de características, en cambio, decide si *una variante del producto* incorpora esas funciones.
* Por eso *una propiedad opcional en Swift no es suficiente para implementar variabilidad de una LPS*.

=== Paso 3. Diferenciar variabilidad en compilación y en ejecución

Más adelante podremos decidir las características antes de compilar:

[source,swift]
----
#if TASKAPP_DUE_DATE
// Compilar el código de la característica Fecha de vencimiento.
#endif
----

Esa condición solo será verdadera si se proporciona la condición de compilación adecuada (por ejemplo, `-D TASKAPP_DUE_DATE`). No equivale a activar una funcionalidad en una pantalla mediante un botón.

En la *sesión 4* introduciremos otra técnica, los *feature flags*, para controlar partes de la interfaz durante la ejecución.

== Primera versión de MVVM: Model, View y ViewModel

Este apartado conecta el modelo con la interfaz y construye la *primera versión* de MVVM de TaskApp Pro: empezamos por el Model, creamos una View sencilla y después extraemos su estado a un ViewModel. Después añadimos dos operaciones (marcar y añadir una tarea). La sesión 4 lo completará con el resto de operaciones y los feature flags.

=== Paso 1. El Model

Reutilizamos `Task` y `Priority` de la demostración anterior (con `title`, `isCompleted`, `dueDate` y `priority`). No contienen ningún código de interfaz.

=== Paso 2. La View

Primero escribimos la vista con los datos *dentro de ella*, para ver qué problema resuelve el ViewModel.

[source,swift]
----
import SwiftUI

@main
struct TaskApp: App {
    var body: some Scene {
        WindowGroup {
            TaskListView()
        }
    }
}

struct TaskListView: View {
    let tasks = [
        Task(title: "Preparar clase"),
        Task(title: "Revisar prácticas"),
        Task(title: "Publicar materiales")
    ]

    var body: some View {
        List(tasks) { task in
            Text(task.title)
        }
    }
}
----

`List` genera una fila por cada `Task`; puede hacerlo sin más parámetros porque `Task` es `Identifiable` (su `id` es el `UUID`). `WindowGroup` crea la ventana de la aplicación.

El inconveniente es que la vista *posee los datos*: si más adelante hay que añadir, completar o borrar tareas, esa lógica acabaría dentro de la pantalla.

=== Paso 3. El ViewModel

Movemos la colección a una clase observable. Es el *ViewModel*: guarda el estado de la pantalla y avisa a la View cuando cambia.

[source,swift]
----
import Observation

@Observable
final class TaskListViewModel {
    var tasks: [Task] = [
        Task(title: "Preparar clase"),
        Task(title: "Revisar prácticas"),
        Task(title: "Publicar materiales")
    ]
}
----

* `@Observable` es una macro del framework *Observation*: hace que la clase notifique cambios a las vistas que la usan.
* No hace falta marcar cada propiedad: todas las propiedades almacenadas de la clase son observables, y la View se redibuja cuando cambia una que lee (aquí, `tasks`).

=== Paso 4. Conectar la View con el ViewModel

[source,swift]
----
struct TaskListView: View {
    @State private var viewModel = TaskListViewModel()

    var body: some View {
        List(viewModel.tasks) { task in
            Text(task.title)
        }
    }
}
----

`@State` crea el ViewModel y lo mantiene mientras exista la vista, que se redibuja cuando cambia alguna propiedad observable que lee. La pantalla es idéntica, pero ahora los datos viven fuera de la vista: es la estructura de MVVM que usaremos a partir de ahora, y sobre ella añadimos las dos primeras operaciones.

=== Paso 5. Marcar una tarea como completada

La operación vive en el *ViewModel*; la View solo avisa de que el usuario ha pulsado.

[source,swift]
----
@Observable
final class TaskListViewModel {
    var tasks: [Task] = [ /* ... */ ]

    func toggleCompletion(id: UUID) {
        guard let index = tasks.firstIndex(where: { $0.id == id }) else { return }
        tasks[index].isCompleted.toggle()
    }
}
----

Recibe el `id`, no la posición en la lista, para no depender del orden en que se muestren las tareas. En la vista, cada fila lleva un botón que llama al ViewModel:

[source,swift]
----
List(viewModel.tasks) { task in
    HStack {
        Button {
            viewModel.toggleCompletion(id: task.id)
        } label: {
            Image(systemName: task.isCompleted ? "checkmark.circle.fill" : "circle")
        }
        .buttonStyle(.plain)
        Text(task.title)
    }
}
----

Al cambiar `isCompleted` dentro de `tasks`, la View se redibuja sola: no hay que decirle que se actualice.

=== Paso 6. Añadir una tarea

De momento la operación solo crea una tarea de ejemplo, sin pedir datos al usuario.

[source,swift]
----
func addTask() {
    tasks.append(Task(title: "Tarea de ejemplo"))
}
----

Y un botón en la vista, debajo de la lista:

[source,swift]
----
struct TaskListView: View {
    @State private var viewModel = TaskListViewModel()

    var body: some View {
        VStack {
            List(viewModel.tasks) { task in
                // fila con el botón de completar
            }
            Button("Añadir tarea") {
                viewModel.addTask()
            }
            .padding()
        }
    }
}
----

El flujo es el del diagrama: la View llama al ViewModel, el ViewModel modifica el Model y la View se redibuja.

=== Comparativa: `ObservableObject` (antes) y `@Observable` (ahora)

Hasta iOS 16 / macOS 13 el ViewModel se escribía con `ObservableObject` y `@Published`, del framework *Combine*. Desde Swift 5.9 (iOS 17 / macOS 14) se usa la macro `@Observable`, del framework *Observation*. El patrón MVVM es el mismo; cambia cómo se declara y cómo se enlaza.

*Modelo anterior*

[source,swift]
----
import Combine

final class TaskListViewModel: ObservableObject {
    @Published var tasks: [Task] = []
}

struct TaskListView: View {
    @StateObject var viewModel = TaskListViewModel()
    // ...
}
----

*Modelo actual*

[source,swift]
----
import Observation

@Observable
final class TaskListViewModel {
    var tasks: [Task] = []
}

struct TaskListView: View {
    @State private var viewModel = TaskListViewModel()
    // ...
}
----

[cols="2,3,3",options="header"]
|===
| Aspecto | Antes: `ObservableObject` | Ahora: `@Observable`

| Framework
| Combine
| Observation

| Declarar el ViewModel
| `class X: ObservableObject`
| `@Observable class X`

| Propiedades observables
| Cada una se marca con `@Published`.
| Todas las propiedades almacenadas lo son. Para excluir una se usa `@ObservationIgnored`.

| Quién crea y conserva el ViewModel en la View
| `@StateObject`
| `@State`

| Pasarlo a una vista hija
| `@ObservedObject`
| Una propiedad normal (`let` o `var`). Si la hija necesita enlaces `$`, `@Bindable`.

| Compartirlo por el entorno
| `@EnvironmentObject`
| `@Environment`

| Cuándo se redibuja la View
| Cuando cambia *cualquier* propiedad `@Published`, aunque la vista no la use.
| Solo cuando cambia una propiedad que la vista *lee* en su `body`.

| Versión mínima
| iOS 13 / macOS 10.15
| iOS 17 / macOS 14
|===

La idea clave: con `@Observable` hay menos anotaciones y la View se actualiza solo por lo que realmente muestra. Los repositorios y tutoriales anteriores a 2023 usan todavía `ObservableObject`, así que conviene reconocer ambas formas.

=== Qué hay que escribir

. *Model, estado de lectura:* un tipo con tres valores posibles (pendiente, leyendo y terminado) que se pueda recorrer y mostrar con un texto legible.
