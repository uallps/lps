En la sesión 3 creamos el proyecto (Xcode en macOS y `Package.swift` en Linux y Windows) y el primer listado con MVVM. Hoy usamos ese mismo proyecto para el primer mecanismo de variabilidad: que de un único código salgan *varios productos*, y que una característica pueda activarse *en ejecución* (feature flags) o *en compilación* (variables de compilación, targets, traits y schemes).

== Feature flags: variabilidad en ejecución y en compilación

Un *feature flag* es una configuración que determina si una característica está activa en un producto.

[cols="1,3",options="header"]
|===
| Situación | Resultado

| `showDueDates = false`
| TaskApp sigue funcionando, pero no muestra la fecha de vencimiento.

| `showDueDates = true`
| Las tareas con fecha muestran ese dato adicional.

| `enableProgress = false`
| BookApp mantiene su biblioteca sin mostrar la información de páginas.

| `enableProgress = true`
| La variante de BookApp puede mostrar datos de avance para los libros que los tengan.
|===

Hay dos técnicas, y se diferencian en *cuándo se decide*:

[cols="1,2,2",options="header"]
|===
| | Variabilidad en ejecución | Variabilidad en compilación

| Cuándo se decide
| Con la aplicación funcionando.
| Antes de compilar.

| Cómo se escribe
| Un valor observable (`AppConfig`) que la vista consulta con un `if`.
| Una condición de compilación y un `#if`.

| Para cambiarla
| Se cambia el valor; la View se actualiza *sin recompilar*.
| Hay que *recompilar* el producto.

| Qué pasa con el código desactivado
| Sigue dentro del programa.
| No existe en el programa.
|===

=== Feature flags en ejecución: AppConfig

La configuración pertenece a la aplicación, *no* al modelo de datos. Es una clase `@Observable` más, en `Application/AppConfig.swift`:

[source,swift]
----
import Observation

/// Feature flags en ejecución: qué características muestra la app.
/// Es configuración de la aplicación, no datos de las tareas.
@Observable // <1>
final class AppConfig {
    var showDueDates = true // <2>
    var showPriorities = true
}
----
<1> Igual que el ViewModel: las vistas que lean un flag se redibujan cuando cambia.
<2> Cada propiedad es un flag. Su valor inicial es el de la variante por defecto.

El ViewModel de la sesión 3 solo cambia en los datos de ejemplo, que ahora tienen fecha y prioridad para que se vea el efecto de los flags:

[source,swift]
----
var tasks: [Task] = [
    Task(title: "Preparar clase", dueDate: Date(timeIntervalSince1970: 1_794_700_800), priority: .high),
    Task(title: "Revisar prácticas", priority: .medium),
    Task(title: "Publicar materiales")
]
----

==== La fila, en una vista propia

La fila de la sesión 3 crece (fecha, prioridad, tachado) y la lista se vuelve difícil de leer. La extraemos a su propia vista en tres pasos:

. *Crear el `struct`* con lo que la fila necesita para dibujarse, como propiedades `let`: la tarea y los flags.
. *Mover* el `HStack` de la lista al `body` de la vista nueva, tal cual.
. *Sustituir* lo que llamaba al ViewModel (`viewModel.toggleCompletion(id:)`) por una propiedad de tipo *closure*, `toggleCompletion: () -> Void`. La lista le pasa qué hacer.

Antes, la fila estaba dentro de la lista y llamaba al ViewModel:

[source,swift]
----
List(viewModel.tasks) { task in
    HStack {
        Button {
            viewModel.toggleCompletion(id: task.id)
        } label: {
            Image(systemName: task.isCompleted ? "checkmark.circle.fill" : "circle")
        }
        .buttonStyle(.plain)
        Text(task.title)
    }
}
----

Después, en `Core/Views/TaskRowView.swift`, recibe la tarea, los flags y la acción, y *no conoce el ViewModel*:

[source,swift]
----
import SwiftUI

/// Fila de una tarea. No conoce el ViewModel: recibe los flags y la acción.
struct TaskRowView: View {
    let task: Task
    let showDueDates: Bool // <1>
    let showPriorities: Bool
    let toggleCompletion: () -> Void // <2>

    var body: some View {
        HStack {
            Button(action: toggleCompletion) { // <3>
                Image(systemName: task.isCompleted ? "checkmark.circle.fill" : "circle")
            }
            .buttonStyle(.plain)
            VStack(alignment: .leading) {
                Text(task.title)
                    .strikethrough(task.isCompleted) // <4>
                if showDueDates, let dueDate = task.dueDate { // <5>
                    Text("Vence: \(dueDate.formatted(date: .abbreviated, time: .shortened))")
                        .font(.caption)
                        .foregroundColor(.secondary)
                }
#if Prioridades // <6>
                if showPriorities, let priority = task.priority {
                    Text("Prioridad: \(priority.rawValue)")
                        .font(.caption)
                        .foregroundColor(priorityColor(for: priority))
                }
#endif
            }
        }
    }

#if Prioridades
    private func priorityColor(for priority: Priority) -> Color { // <7>
        switch priority {
        case .low: return .green
        case .medium: return .yellow
        case .high: return .red
        }
    }
#endif
}
----
<1> Los flags llegan como valores normales: la fila no sabe de dónde vienen.
<2> La acción de marcar llega como *closure*. La fila avisa de que el usuario ha pulsado; quien la crea decide qué hacer.
<3> El botón ejecuta la closure recibida.
<4> El título se tacha cuando la tarea está completada.
<5> *Punto de variación en ejecución:* la fecha solo se muestra si el flag está activo *y* la tarea tiene fecha.
<6> *Punto de variación en compilación:* este bloque solo existe en los productos que definen `Prioridades` (lo vemos más abajo).
<7> La función auxiliar también va dentro del `#if`: si no, el producto base tendría código que nadie usa.

==== La lista, con los flags

La lista guarda el `AppConfig` en un `@State`, igual que el ViewModel, y ofrece un botón por flag:

[source,swift]
----
import SwiftUI

struct TaskListView: View {
    @State private var viewModel = TaskListViewModel()
    @State private var config = AppConfig() // <1>

    var body: some View {
        VStack {
            HStack {
                Button("Fechas: \(config.showDueDates ? "Sí" : "No")") { // <2>
                    config.showDueDates.toggle()
                }
#if Prioridades // <3>
                Button("Prioridades: \(config.showPriorities ? "Sí" : "No")") {
                    config.showPriorities.toggle()
                }
#endif
            }
            .padding(.top)
            List(viewModel.tasks) { task in
                TaskRowView( // <4>
                    task: task,
                    showDueDates: config.showDueDates,
                    showPriorities: config.showPriorities,
                    toggleCompletion: { viewModel.toggleCompletion(id: task.id) } // <5>
                )
            }
            Button("Añadir tarea") {
                viewModel.addTask()
            }
            .padding()
        }
    }
}
----
<1> La pantalla crea y conserva la configuración.
<2> Cambiar el flag redibuja las filas *sin recompilar*: es variabilidad en ejecución.
<3> El botón de prioridades solo existe en el producto que compila la característica.
<4> La fila recibe los valores actuales de los flags.
<5> La closure llama al ViewModel. La fila sigue sin conocerlo.

.TaskApp Prioridades con el flag de prioridades apagado: la característica está compilada, pero no se muestra
image::s4-taskapp-macos-prioridades-off.png[TaskApp Prioridades con Prioridades: No, width=60%]

*Pregunta:* ¿es lo mismo que la fecha sea `nil` a que la feature esté desactivada? No: el primer caso es el dato de una tarea y el segundo la configuración del producto.

=== Variables de compilación

Una *variable de compilación* (_compilation condition_) es un nombre que se activa al compilar. Desde el código se consulta con `#if`; si no está activa, el compilador *no incluye* ese bloque. Es lo que hemos usado con `#if Prioridades`.

Hay varias formas de definirla:

[cols="2,3,3",options="header"]
|===
| Dónde | Cómo | Ejemplo

| *Xcode*
| Ajuste *Active Compilation Conditions* del target, en *Build Settings*.
| `Prioridades`

| *Trait* de `Package.swift`
| Cada trait activo es una variable con su nombre.
| `swift run --traits Prioridades TaskApp`

| *`Package.swift`*
| `swiftSettings` del target, con `.define`. Se puede limitar a una configuración.
| `.define("Prioridades", .when(configuration: .debug))`

| *Línea de comandos*
| Se pasa la opción `-D` al compilador.
| `swift run -Xswiftc -DPrioridades TaskApp`

| *Automática*
| Swift define `DEBUG` en las compilaciones de depuración de Xcode y de SwiftPM.
| `#if DEBUG`
|===

Todas producen el mismo efecto: la variable llega al `#if`. Para TaskApp usamos la primera en Xcode y la segunda en Linux y Windows, porque las dos crean un *producto con nombre propio*.

== Un proyecto, varios productos

Queremos que el producto base y *TaskApp Prioridades* salgan *del mismo código*: misma carpeta `TaskApp/`, sin copiar ficheros. Lo único que cambia es qué variables de compilación están activas.

=== En Xcode: un target por producto

Un *target* es lo que Xcode sabe construir: una app con su nombre, su identificador y sus ajustes de compilación. Cada producto de la línea es un target, y todos comparten la carpeta `TaskApp/`.

. Seleccionad el proyecto en el navegador. En la lista *TARGETS*, clic derecho sobre `TaskApp` y *Duplicate*.
+
image::s4-xcode-duplicar-target.png[Menú Duplicate sobre el target TaskApp, width=70%]

. Xcode crea el target `TaskApp copy`. Seleccionadlo, pulsad Intro y renombradlo a `TaskApp Prioridades`.
. En el target nuevo, pestaña *Build Settings*, buscad `Active Compilation Conditions` y añadid `Prioridades` en *Debug* y en *Release*.
+
image::s4-xcode-condiciones.png[Active Compilation Conditions del target TaskApp Prioridades: Prioridades en Debug y en Release]

. En la pestaña *General* del target nuevo, cambiad el *Bundle Identifier* a `es.ual.TaskApp.Prioridades`, para que el sistema lo trate como otra app.

Como la carpeta `TaskApp/` es una carpeta sincronizada, *todos sus ficheros pertenecen a los dos targets*: lo podéis ver en el inspector de la derecha (*Target Membership*) al seleccionar un fichero.

=== Schemes: elegir qué producto se lanza

Un *scheme* es una configuración guardada de Xcode que define *qué* se construye y se ejecuta y *con qué opciones*: el target, la configuración de compilación (Debug o Release), los argumentos y las variables de entorno. Al duplicar el target, Xcode crea su scheme, que toma el nombre del target. Para lanzar un producto, se elige su scheme en la barra superior y se pulsa ▶:

image::s4-xcode-schemes.png[Menú de schemes con TaskApp y TaskApp Prioridades, width=60%]

Desde la terminal, cada producto se compila con su scheme:

[source,shell]
----
xcodebuild -project TaskApp.xcodeproj -scheme "TaskApp" build
xcodebuild -project TaskApp.xcodeproj -scheme "TaskApp Prioridades" build
----

=== En `Package.swift`: un trait por característica

Swift Package Manager no compila dos veces la misma carpeta con dos targets. Para Linux y Windows usamos *traits* (SwiftPM 6.1 o superior): opciones que se activan al compilar y que llegan al código como variables de compilación.

[source,swift]
----
let package = Package(
    name: "TaskApp",
    // Productos de la línea: cada trait activo es una variable de compilación (#if Prioridades).
    // En Xcode, el mismo papel lo cumple el target «TaskApp Prioridades».
    traits: [ // <1>
        .trait(name: "Prioridades", description: "Característica opcional: prioridad de la tarea"), // <2>
    ],
    dependencies: [
        .package(url: "https://github.com/uallps/SwiftOpenUI.git", branch: "uallps"),
    ],
    // ... targets igual que en la sesión 3
)
----
<1> `traits:` declara las variantes que se pueden activar al compilar. Va entre `name:` y `dependencies:`.
<2> El nombre del trait es el de la variable de compilación: activar el trait `Prioridades` hace verdadero `#if Prioridades`.

Sin traits se compila el producto base; con `--traits` se elige la variante:

[source,shell]
----
swift run TaskApp                           # producto base
swift run --traits Prioridades TaskApp      # TaskApp Prioridades
----

[IMPORTANT]
====
Las opciones de `swift run` van *antes* del nombre del ejecutable. Lo que se escribe después (`swift run TaskApp --traits Prioridades`) se le pasa a la app como argumento y no activa nada.
====

Así conviven dos niveles de variabilidad: el target o el trait `Prioridades` deciden si el código *existe*, y el flag `showPriorities` decide, en un producto que sí lo incluye, si se *muestra*.

[cols="1,2,2",options="header"]
|===
| Producto | macOS (Xcode) | Linux y Windows

| Base
| Scheme `TaskApp`
| `swift run TaskApp`

| Con prioridades
| Scheme `TaskApp Prioridades`
| `swift run --traits Prioridades TaskApp`
|===

== Actividad: BookApp con dos productos

Partiendo del listado de libros de la sesión 3, cread el segundo producto de BookApp y usad los feature flags para la primera característica común, *F1: Progreso*.

=== Qué hay que hacer

. *Operaciones del listado:* cambiar el estado de lectura de un libro y añadir un libro de ejemplo, en el ViewModel.
. *Fila propia:* extraed la fila del libro a una vista que reciba el libro, los flags y la acción como closure, sin conocer el ViewModel.
. *Declarar los cinco flags comunes* (F1–F5) en una configuración `@Observable` de la aplicación, todos desactivados.
. *Implementar F1* como componente independiente: sus datos (libro, total de páginas y página actual) y su ViewModel *no* pueden ir dentro del libro ni del ViewModel del listado. La vista solo muestra el progreso si el flag de F1 está activo.
. *Hacer F1 variable en compilación* con `#if Progreso`, y comprobad que sin esa variable el código de F1 no se compila.
. *Segundo producto en Xcode:* duplicad el target como `BookApp Progreso`, con `Progreso` en *Active Compilation Conditions* y su propio *Bundle Identifier*.
. *Segundo producto en `Package.swift`:* declarad el trait `Progreso` y comprobad `swift run BookApp` y `swift run --traits Progreso BookApp`.

=== Comprobad vuestro diseño

* ¿En qué se parece un target (o un trait) a un feature flag y en qué se diferencia? Pensad en *cuándo* se decide cada uno.
* Con F1 desactivada, ¿siguen funcionando la biblioteca y los datos del libro? ¿Y con F1 sin compilar?
* ¿Dónde viven los datos de progreso y por qué no en el libro?
* ¿Por qué la fila recibe una closure en lugar del ViewModel?
* ¿Qué pasaría si copiarais la carpeta `BookApp/` para hacer el segundo producto en vez de duplicar el target?

| Qué se evalúa | Qué debéis demostrar
