== Teoría: Modelos de Características (Cap. 3 y 4)

Un Modelo de Características es una estructura de árbol que representa todas las características de una Línea de Productos Software (LPS) y las relaciones entre ellas. Es la principal herramienta para definir y gestionar la variabilidad.

=== ¿Qué es una Característica (Feature)?

Una característica es una unidad de funcionalidad visible para el usuario o un stakeholder. Es algo que un producto "hace" o "tiene". Ejemplos: "Guardar en la nube", "Modo oscuro", "Notificaciones push".

=== El Diagrama de Características

Es la representación visual del modelo. Se lee de arriba abajo, descomponiendo características complejas en otras más simples.

.Componentes Principales
- **Raíz (Root):** El nodo superior, que representa el producto o la LPS en su conjunto.
- **Características Hijas:** Descomposición de una característica padre.
- **Relaciones de Variabilidad:** Definen cómo se pueden seleccionar las características hijas.

=== Notación del Diagrama

[cols="1,3"]
|===
| Símbolo | Descripción

| *Característica Obligatoria (Mandatory)*
| Un círculo relleno (`●`). Si se elige el padre, esta característica *debe* ser incluida. Es una relación 1 a 1.

| *Característica Opcional (Optional)*
| Un círculo vacío (`○`). Si se elige el padre, esta característica *puede o no* ser incluida. Es una relación 0 a 1.

| *Grupo Alternativo (Alternative / XOR)*
| Un arco que conecta varias características opcionales. Si se elige el padre, *exactamente una* de las características del grupo debe ser seleccionada.

| *Grupo Opcional Múltiple (Or)*
| Un arco relleno que conecta varias características opcionales. Si se elige el padre, *una o más* de las características del grupo pueden ser seleccionadas.
|===

=== Restricciones Cruzadas (Cross-Tree Constraints)

A veces, la selección de una característica en una rama del árbol afecta a otra en una rama diferente.

- `requires`: La selección de la característica A implica que la característica B también debe ser seleccionada.
- `excludes`: La selección de la característica A impide que la característica B sea seleccionada.

=== Estructura de Directorios MVVM para "TaskApp Pro"

Esta estructura organiza el proyecto siguiendo el patrón MVVM y está diseñada para soportar la arquitectura de Línea de Productos Software, separando el núcleo de la aplicación de las features opcionales (plugins).

----
TaskApp/
├── 📁 Application/
│   ├── 📄 TaskApp.swift               // Punto de entrada de la app (@main)
│   └── 📄 AppConfig.swift             // GESTOR DE FEATURE FLAGS
│
├── 📁 Core/
│   ├── 📁 Models/
│   │   ├── 📄 Task.swift              // El modelo de datos principal (M)
│   │   ├── 📄 Priority.swift         // Enum para la prioridad
│   │   └── 📄 TaskState.swift         // Enum para el estado
│   │
│   ├── 📁 Views/
│   │   ├── 📄 TaskListView.swift     // La vista principal que muestra la lista (V)
│   │   └── 📄 TaskRowView.swift       // La vista para una sola fila en la lista (V)
│   │
│   └── 📁 ViewModels/
│       └── 📄 TaskListViewModel.swift // Lógica y estado para TaskListView (VM)
│
├── 📁 Features/
│   ├── 📁 DueDate/
│   │   ├── 📁 Views/
│   │   │   └── 📄 DatePickerView.swift
│   │   └── 📁 .../
│   │
│   ├── 📁 Reminders/
│   │   ├── 📁 Views/
│   │   │   └── 📄 ReminderSettingsView.swift
│   │   └── 📁 .../
│   │
│   └── 📁 .../ (Otras carpetas para cada feature)
│
├── 📁 Infrastructure/
│   ├── 📁 Persistence/
│   │   ├── 📄 StorageProvider.swift        // El protocolo ("enchufe")
│   │   ├── 📄 JSONStorageProvider.swift     // Plugin 1
│   │   └── 📄 SwiftDataStorageProvider.swift // Plugin 2
│   │
│   └── 📁 Plugins/
│       ├── 📄 PluginRegistry.swift         // Registra todos los plugins activos
│       ├── 📄 RowComponentPlugin.swift     // Protocolo para plugins de UI
│       └── 📄 TaskDataObservingPlugin.swift // Protocolo para plugins de datos
│
└── 📁 Utils/
    └── 📄 Date+Extensions.swift          // Helpers y extensiones
----

==== Explicación de las Carpetas

📁 **Application**: Contiene la configuración global de la aplicación. Aquí vive el fichero `@main` que arranca todo y, muy importante, nuestro `AppConfig.swift`, el "cuadro de mandos" de los feature flags.

📁 **Core**: Es el corazón de la aplicación, con la funcionalidad mínima que tendrán todos los productos. Está organizado siguiendo estrictamente MVVM:

- **Models**: Las estructuras de datos principales (`Task`, `Priority`, etc.).
- **Views**: Las vistas de SwiftUI que siempre estarán presentes (`TaskListView`).
- **ViewModels**: La lógica que maneja esas vistas (`TaskListViewModel`).

📁 **Features**: ¡Aquí es donde vive la LPS! Cada subcarpeta (`DueDate`, `Reminders`) es un módulo autocontenido que representa una feature opcional. Internamente, cada una puede seguir su propia mini-estructura MVVM.

📁 **Infrastructure**: Es la "fontanería" que permite que todo funcione.

- **Persistence**: Contiene el "contrato" (`StorageProvider`) y las dos implementaciones intercambiables (JSON y SwiftData).
- **Plugins**: Aquí definimos las "interfaces" de nuestros plugins. El `PluginRegistry` es el cerebro que sabe qué plugins están "enchufados" en cada momento.

📁 **Utils**: Una carpeta de utilidades para código reutilizable que no encaja en ningún otro sitio.

=== Traducción a Modelo de Datos Swift

Este diagrama nos sirve de guía para crear nuestras estructuras en Swift. Las características se convierten en propiedades de nuestros `structs`. Vamos a construir el modelo paso a paso, empezando por lo obligatorio, luego lo opcional, y finalmente la compilación condicional.

==== Paso 1: Modelo Base Obligatorio
Empezamos con la estructura base que representa las características obligatorias: un ID único, el título de la tarea y su estado de completitud.

[source,swift]
----
struct Tarea {
    let id: UUID = UUID()  <1>
    var titulo: String
    var completada: Bool = false  <2>
}
----
<1> **UUID**: Identificador Único Universal. `UUID()` genera un ID único cada vez que se crea una instancia de `Tarea`. Es `let` (inmutable) para asegurar que el ID no cambie nunca.
<2> **Valor por defecto**: `= false` asigna `false` como valor inicial si no se especifica otro al crear la tarea. Indica que la tarea no está completada por defecto.

Esta estructura define lo mínimo necesario para cualquier tarea en TaskApp Pro. El `id` es único e inmutable, `titulo` es requerido, y `completada` indica si la tarea está terminada.

==== Paso 2: Añadiendo Propiedades Opcionales
Ahora añadimos las propiedades opcionales basadas en las características opcionales del diagrama. Usamos tipos opcionales (`?`) para representar que estas propiedades pueden no estar presentes.

[source,swift]
----
struct Tarea {
    let id: UUID = UUID()
    var titulo: String
    var completada: Bool = false
    var fechaVencimiento: Date?  <1>
    var prioridad: Prioridad?  <2>
}

enum Prioridad {
    case baja, media, alta  <3>
}
----
<1> **Propiedad opcional**: `Date?` permite que `fechaVencimiento` sea `nil` si no se establece, representando una característica opcional.
<2> **Propiedad opcional**: `Prioridad?` es opcional y usa el enum definido abajo.
<3> **Enum**: Define los posibles valores para la prioridad, permitiendo solo `baja`, `media` o `alta`.

Hemos añadido `fechaVencimiento` y `prioridad` como opcionales. El enum `Prioridad` define los posibles valores para la prioridad de una tarea.

==== Paso 3: Compilación Condicional con `#if`
Para representar cómo las características opcionales pueden activarse o desactivarse en diferentes productos, usamos directivas de compilación condicional. Esto permite incluir o excluir código basado en módulos disponibles.

[source,swift]
----
struct Tarea {
    let id: UUID = UUID()
    var titulo: String
    var completada: Bool = false
    #if canImport(Fechas)  <1>
    var fechaVencimiento: Date?
    #endif
    #if canImport(Prioridades)  <2>
    var prioridad: Prioridad?
    #endif
}

#if canImport(Prioridades)  <3>
enum Prioridad {
    case baja, media, alta
}
#endif
----
<1> **Compilación condicional**: `#if canImport(Fechas)` incluye `fechaVencimiento` solo si el módulo `Fechas` está disponible, permitiendo variabilidad en el producto.
<2> **Compilación condicional**: Similarmente, incluye `prioridad` solo si `Prioridades` está disponible.
<3> **Compilación condicional del enum**: El enum `Prioridad` se define solo si el módulo `Prioridades` está disponible, evitando código innecesario.

NOTE: Este uso de `#if canImport(...)` es un ejemplo simplificado para ilustrar la variabilidad en tiempo de compilación. En sesiones posteriores veremos técnicas más avanzadas para gestionar la variabilidad de productos. Aquí se trata de deshabilitar características opcionales en tiempo de compilación, excluyendo el código correspondiente si los módulos no están disponibles.
