== Teoría: Navegación, paso de datos y Git Flow (30 min)

=== Navegar entre pantallas

Navegar es cambiar la vista que se muestra y poder volver a la anterior. `NavigationStack` es el contenedor con una *pila* de pantallas: se «empuja» una vista nueva y se «saca» para volver. Existe en SwiftUI y en SwiftCrossUI, pero con una API distinta:

[cols="2,3,3",options="header"]
|===
| | SwiftUI | SwiftCrossUI

| Crear la pila
| `NavigationStack { ... }`
| `NavigationStack(path: $path) { ... }`: la ruta es *obligatoria*.

| Enlace a otra pantalla
| `NavigationLink(destination: Vista()) { ... }` o `NavigationLink(titulo, value: valor)`
| `NavigationLink(titulo, value: valor, path: $path)`: recibe la ruta y el texto es un `String`.

| Dónde se declara el destino
| Dentro del `NavigationLink` o con `.navigationDestination(for:)` sobre el contenido de la pila.
| `.navigationDestination(for:)` sobre la propia `NavigationStack`.

| Botón de volver
| Lo añade el sistema.
| No existe: se hace con `path.removeLast()`.

| Título y formularios
| `.navigationTitle` y `Form`.
| No existen.

| Valor de la ruta
| `Hashable`
| `Codable`
|===

Como la forma de escribirlo cambia, la navegación *no se puede compartir*. Igual que la fila de la sesión anterior, se escribe una versión en cada carpeta de vistas, con el mismo nombre y la misma API pública, y *sin `#if`* entre versiones. La aplicación solo llama a `TaskListView()` y recibe la de la versión activa.

=== Paso de datos entre vistas

[cols="1,3",options="header"]
|===
| Mecanismo | Cuándo se usa

| Inicializador simple
| La vista hija solo *lee* el dato.

| `@Binding`
| La vista hija *modifica* un valor que pertenece a la vista padre.

| `@Bindable`
| La vista hija edita las propiedades de un objeto `@Observable` y necesita bindings con `$`.

| Closure
| La vista hija *avisa* de una acción (como volver) sin conocer a quien la gestiona.
|===

*`@Binding`.* La vista padre crea el binding y la hija lo recibe. En SwiftUI, `List($viewModel.tasks) { $task in ... }` da un binding por tarea:

[source,swift]
----
struct TaskDetailView: View {
    @Binding var task: Task

    var body: some View {
        Form {
            TextField("Título de la tarea", text: $task.title)
        }
    }
}
----

*`@Bindable`.* Si el dato es un objeto `@Observable`, se declara con `@Bindable` y se obtienen bindings de sus propiedades:

[source,swift]
----
@Observable
final class Borrador {
    var titulo = ""
}

struct EditorView: View {
    @Bindable var borrador: Borrador

    var body: some View {
        TextField("Título", text: $borrador.titulo)
    }
}
----

=== Flujo de trabajo con Git Flow

Git Flow es un modelo de ramas que ayuda a organizar el desarrollo en equipo. Las ramas principales son:

* *`main`:* el código estable.
* *`develop`:* la rama de integración de las nuevas características.
* *`feature/`:* se crean a partir de `develop` para trabajar en una característica. Cuando está terminada, se fusiona de nuevo en `develop`.

En nuestro proyecto cada característica (F1, F2… y las originales) tiene su rama. Hay dos puntos que conviene cuidar:

* *No se suben las compilaciones.* El `.gitignore` debe incluir `.build/`. El fichero `Package.resolved` sí se sube.
* *El `Package.swift` lo tocará todo el mundo.* Cada característica puede añadir un trait, así que es el fichero donde más conflictos aparecerán al integrar. Se resuelven conservando los traits de las dos ramas.

== Demostración: detalle de tarea en TaskApp Pro (1 h 15 min)

Partimos del paquete de la sesión 4 (`TaskCore`, las dos carpetas de vistas, `TaskUI` y `TaskApp`). Añadimos una pantalla de detalle para editar el título de una tarea y la navegación hasta ella, con una vista propia en cada versión.

=== Paso 1: la vista de detalle, una por versión

*Versión SwiftUI* (`TaskViewsSwiftUI/TaskDetailView.swift`): un `Form` cuyo título de ventana es el título de la tarea.

[source,swift]
----
import SwiftUI
import TaskCore

struct TaskDetailView: View {
    @Binding var task: Task

    var body: some View {
        Form {
            TextField("Título de la tarea", text: $task.title)
        }
        .navigationTitle($task.title)
    }
}
----

*Versión SwiftCrossUI* (`TaskViewsSwiftCrossUI/TaskDetailView.swift`): sin `Form` ni `.navigationTitle`, y la pila no añade un botón de volver, así que la vista recibe una acción para volver.

[source,swift]
----
import SwiftCrossUI
import TaskCore

/// SwiftCrossUI no tiene `Form` ni `.navigationTitle` y la pila no añade un
/// botón de volver: la vista recibe una acción para volver.
struct TaskDetailView: View {
    @Binding var task: Task
    let close: () -> Void

    var body: some View {
        VStack {
            Text(task.title)
                .font(.title)
            TextField("Título de la tarea", text: $task.title)
            Button("Volver") {
                close()
            }
        }
        .padding()
    }
}
----

=== Paso 2: la lista con navegación, una por versión

*Versión SwiftUI* (`TaskViewsSwiftUI/TaskListView.swift`), con el `NavigationStack` y el `NavigationLink` del curso anterior:

[source,swift]
----
import SwiftUI
import TaskCore

public struct TaskListView: View {
    @State private var viewModel = TaskListViewModel()
    @State private var config = AppConfig()

    public init() {}

    public var body: some View {
        NavigationStack {
            List($viewModel.tasks) { $task in
                NavigationLink(destination: TaskDetailView(task: $task)) {
                    TaskRowView(
                        task: task,
                        showDueDates: config.showDueDates,
                        showPriorities: config.showPriorities,
                        toggleCompletion: {
                            viewModel.toggleCompletion(id: task.id)
                        }
                    )
                }
            }
            .toolbar {
                Toggle("Fechas", isOn: $config.showDueDates)
                Toggle("Prioridades", isOn: $config.showPriorities)
                Button("Añadir Tarea") {
                    viewModel.addTask()
                }
            }
            .navigationTitle("Tareas")
        }
    }
}
----

*Versión SwiftCrossUI* (`TaskViewsSwiftCrossUI/TaskListView.swift`): la pila con ruta, `NavigationLink` con la ruta, el destino sobre la pila y el binding de la tarea por identificador.

[source,swift]
----
import Foundation
import SwiftCrossUI
import TaskCore

/// En SwiftCrossUI `NavigationStack` exige una ruta, `NavigationLink` recibe esa
/// ruta y el destino se declara sobre la propia pila.
public struct TaskListView: View {
    @State var viewModel = TaskListViewModel()
    @State var config = AppConfig()
    @State var path = NavigationPath()

    public init() {}

    public var body: some View {
        NavigationStack(path: $path) {
            VStack(alignment: .leading) {
                Text("Tareas")
                    .font(.title)
                HStack {
                    Toggle("Fechas", isOn: $config.showDueDates)
                    Toggle("Prioridades", isOn: $config.showPriorities)
                    Button("Añadir Tarea") {
                        viewModel.addTask()
                    }
                }
                ForEach(viewModel.tasks) { task in
                    HStack {
                        TaskRowView(
                            task: task,
                            showDueDates: config.showDueDates,
                            showPriorities: config.showPriorities,
                            toggleCompletion: {
                                viewModel.toggleCompletion(id: task.id)
                            }
                        )
                        NavigationLink("Detalle", value: task.id, path: $path)
                    }
                }
            }
            .padding()
        }
        .navigationDestination(for: UUID.self) { id in
            TaskDetailView(task: binding(for: id), close: { path.removeLast() })
        }
    }

    private func binding(for id: UUID) -> Binding<Task> {
        Binding(
            get: { viewModel.tasks.first { $0.id == id } ?? Task(title: "") },
            set: { newValue in
                guard let index = viewModel.tasks.firstIndex(where: { $0.id == id }) else { return }
                viewModel.tasks[index] = newValue
            }
        )
    }
}
----

Las dos reutilizan `TaskRowView` y `AppConfig`, y las dos tienen la misma API pública: `TaskListView()`.

=== Paso 3: la aplicación no conoce la versión

El ejecutable solo importa la fachada y llama a la vista. No hay ningún `#if` ni ninguna referencia al framework:

[source,swift]
----
import TaskUI

@main
struct TaskApp: App {
    var body: some Scene {
        WindowGroup("TaskApp") {
            TaskListView()
        }
    }
}
----

[source,shell]
----
swift run                           # SwiftUI
swift run --traits SwiftCrossUI     # SwiftCrossUI
----

Preguntas para comentar: ¿qué se escribe una sola vez (modelo, ViewModel, flags) y qué dos veces (navegación, detalle, fila)? ¿Qué hay que hacer a mano en SwiftCrossUI que en SwiftUI hace el sistema (volver, título)? ¿Se ven igual las dos versiones? ¿Por qué no?

=== Paso 4: una rama de Git para una nueva característica

[source,shell]
----
# 1. Situarse en la rama de integración (si no existe: git switch -c develop)
git switch develop

# 2. Crear y cambiar a una rama para la característica
git switch -c feature/task-editing

# 3. Trabajar, y confirmar los cambios con un mensaje descriptivo
git add .
git commit -m "feat: add task detail view"

# 4. Volver a develop e integrar la característica
git switch develop
git merge --no-ff feature/task-editing

# 5. Ver el historial con las ramas
git log --oneline --graph
----

== Actividad: detalle de libro en BookApp con dos productos (1 h 45 min)

Añadid a *BookApp* una pantalla de detalle y la navegación hasta ella, con una vista propia en cada versión (SwiftUI y SwiftCrossUI), y trabajad en ramas de Git.

=== Qué hay que hacer

. *Crear la vista de detalle del libro en cada carpeta de vistas*, que permita modificar al menos el título y el estado de lectura. La de SwiftUI usa un `Form`; la de SwiftCrossUI recibe además una acción para volver.
. *Crear la lista con navegación en cada carpeta de vistas*, de modo que desde el listado se llegue al detalle y se pueda volver. La aplicación solo debe llamar a esa vista, sin `#if`.
. *Comprobar* que lo que se edita en el detalle aparece en el listado al volver.
. *Comprobar los dos productos* con `swift run` y con `swift run --traits SwiftCrossUI`.
. *Trabajar con ramas.* Cada miembro del equipo:
  * crea una rama personal con el formato `feature/nombre-feature-tu-nombre`;
  * hace los cambios en su rama y los confirma con mensajes descriptivos;
  * integra su rama en `develop`.

=== Comprobad vuestro diseño

* ¿Quién es el dueño del dato que se edita: el listado, el detalle o el ViewModel? ¿Qué pasaría si el detalle recibiera una *copia* del libro?
* ¿Qué parte de la navegación tuvisteis que escribir dos veces y qué hace el sistema en SwiftUI que en SwiftCrossUI hay que hacer a mano?
* ¿Dónde deberían ir los datos de una característica opcional (por ejemplo, el progreso) para que el detalle funcione también con ella desactivada?
* ¿Qué ficheros esperáis que den conflicto al integrar las ramas del equipo?
