== Teoría: Navegación, paso de datos y Git Flow (30 min)

=== Navegar entre pantallas

Navegar es cambiar la vista que se muestra y poder volver a la anterior. `NavigationStack` es el contenedor con una *pila* de pantallas: se «empuja» una vista nueva y se «saca» para volver.

[cols="2,5",options="header"]
|===
| Pieza | Qué hace

| `NavigationStack { ... }`
| Crea la pila. Su contenido es la primera pantalla.

| `NavigationLink(destination: Vista()) { ... }`
| Una fila o botón que, al pulsarlo, empuja `Vista()` sobre la pila.

| Botón de volver
| Lo añade el sistema: la flecha de la barra en macOS y el botón *Back* de la barra de GTK en Linux.

| `.navigationTitle("...")`
| El título de la pantalla, que aparece en la barra de la ventana.

| `.toolbar { ... }`
| Botones en la barra de la ventana, junto al título.
|===

Como en macOS es el SwiftUI de Apple y en Linux y Windows es SwiftOpenUI con la misma API, *la navegación se escribe una sola vez*. El aspecto cambia (cada sistema dibuja sus propios controles), pero el comportamiento es el mismo.

=== Paso de datos entre vistas

[cols="1,3",options="header"]
|===
| Mecanismo | Cuándo se usa

| Inicializador simple
| La vista hija solo *lee* el dato.

| `@Binding`
| La vista hija *modifica* un valor que pertenece a la vista padre.

| `@Bindable`
| La vista hija edita las propiedades de un objeto `@Observable` y necesita bindings con `$`.

| Closure
| La vista hija *avisa* de una acción sin conocer a quien la gestiona (lo hicimos con la fila en la sesión 4).
|===

*`@Binding`.* La vista padre crea el binding y la hija lo recibe. En la demostración, la lista lo construye con `binding(for:)`, que lee y escribe la tarea a través del ViewModel.

*Cómo funciona un `Binding`.* Un `Binding<Task>` no guarda la tarea: guarda dos funciones, una para *leerla* (`get`) y otra para *escribirla* (`set`) allí donde vive. En TaskApp, `binding(for:)` las construye a mano: `get` llama a `viewModel.task(id:)` y `set` a `viewModel.updateTask(_:)`. El `$` también crea bindings: `$task.title` enlaza con el título de la tarea. El detalle lo recibe con `@Binding var task: Task`; cada letra que se escribe en el `TextField` pasa por el `set` hasta el ViewModel, y la lista, que observa el ViewModel, se redibuja. Con `let task: Task` el detalle tendría una *copia*: ni siquiera compilaría `$task.title`, porque no habría a dónde escribir.

*`@Bindable`.* Si el dato es un objeto `@Observable`, se declara con `@Bindable` y se obtienen bindings de sus propiedades:

[source,swift]
----
@Observable
final class Borrador {
    var titulo = ""
}

struct EditorView: View {
    @Bindable var borrador: Borrador // <1>

    var body: some View {
        TextField("Título", text: $borrador.titulo) // <2>
    }
}
----
<1> La vista recibe el objeto (no una copia) y puede pedirle bindings.
<2> `$borrador.titulo` es un binding a la propiedad: lo que se escribe cambia el objeto, y toda vista que lo lea se redibuja.

=== Flujo de trabajo con Git Flow

Git Flow es un modelo de ramas que ayuda a organizar el desarrollo en equipo. Las ramas principales son:

* *`main`:* el código estable.
* *`develop`:* la rama de integración de las nuevas características.
* *`feature/`:* se crean a partir de `develop` para trabajar en una característica. Cuando está terminada, se fusiona de nuevo en `develop`.

En nuestro proyecto cada característica (F1, F2… y las originales) tiene su rama. Hay tres puntos que conviene cuidar:

* *No se suben las compilaciones ni los ajustes personales de Xcode.* El `.gitignore` debe incluir `.build/`, `DerivedData/` y `xcuserdata/`. Los ficheros `Package.resolved` sí se suben.
* *`project.pbxproj` y `Package.swift` los tocará todo el mundo.* Cada característica que se compile aparte añade un target en Xcode y un trait en `Package.swift`, así que son los ficheros donde más conflictos aparecerán al integrar. Se resuelven conservando lo de las dos ramas.
* *Los ficheros nuevos no tocan el proyecto.* Gracias a la carpeta sincronizada, añadir un `.swift` dentro de `TaskApp/` no cambia `project.pbxproj`, así que no genera conflictos.

== Demostración: detalle de tarea en TaskApp Pro (1 h 15 min)

Partimos del proyecto de la sesión 4. Añadimos una pantalla de detalle para editar una tarea y la navegación hasta ella. Todo va en `Core/Views/` y se compila igual en los dos productos.

=== Paso 1: la vista de detalle

`Core/Views/TaskDetailView.swift`: un formulario que edita el título y si la tarea está completada.

[source,swift]
----
import SwiftUI

/// Detalle de una tarea. Recibe un enlace (@Binding) a la tarea de la lista:
/// lo que se edita aquí cambia la tarea del ViewModel, sin copias.
struct TaskDetailView: View {
    @Binding var task: Task // <1>

    var body: some View {
        Form { // <2>
            TextField("Título de la tarea", text: $task.title) // <3>
            Toggle("Completada", isOn: $task.isCompleted) // <4>
        }
        .navigationTitle(task.title) // <5>
    }
}
----
<1> La vista no es dueña de la tarea: recibe un *enlace* a la que guarda el ViewModel.
<2> `Form` agrupa los controles de edición con el estilo de formulario de cada sistema.
<3> `$task.title` es un binding a una propiedad de la tarea: cada letra que se escribe cambia la tarea real.
<4> Igual con el estado: marcar la casilla cambia `isCompleted` de la tarea real.
<5> El título de la ventana es el de la tarea, y se actualiza mientras se escribe.

=== Paso 2: la lista con navegación

`TaskListView` mete la lista en un `NavigationStack`, convierte cada fila en un enlace al detalle y pasa los botones a la barra de la ventana. La fila se escribe en una función aparte, `taskRow(task:)`. Además, cada fila tiene un menú contextual para borrar la tarea. El ViewModel gana tres métodos: borrar, leer una tarea por su `id` y sustituirla al editarla en el detalle.

[source,swift]
----
func removeTask(id: UUID) {
    tasks.removeAll { $0.id == id }
}

/// La tarea con ese id, si sigue en la lista.
func task(id: UUID) -> Task? {
    tasks.first { $0.id == id }
}

/// Sustituye la tarea que tiene el mismo id (la usa el detalle al editar).
func updateTask(_ task: Task) {
    guard let index = tasks.firstIndex(where: { $0.id == task.id }) else { return }
    tasks[index] = task
}
----

[source,swift]
----
import SwiftUI

struct TaskListView: View {
    @State private var viewModel = TaskListViewModel()
    @State private var config = AppConfig()

    var body: some View {
        NavigationStack { // <1>
            List {
                ForEach(viewModel.tasks) { task in
                    taskRow(task: task) // <2>
                }
            }
            .toolbar { // <3>
                Button("Fechas: \(config.showDueDates ? "Sí" : "No")") {
                    config.showDueDates.toggle()
                }
#if Prioridades
                Button("Prioridades: \(config.showPriorities ? "Sí" : "No")") {
                    config.showPriorities.toggle()
                }
#endif
                Button("Añadir tarea") {
                    viewModel.addTask()
                }
            }
            .navigationTitle("Tareas") // <4>
        }
    }

    /// Una fila: enlace al detalle de la tarea, con menú contextual para borrarla.
    private func taskRow(task: Task) -> some View {
        NavigationLink(destination: TaskDetailView(task: binding(for: task))) { // <5>
            TaskRowView( // <6>
                task: task,
                showDueDates: config.showDueDates,
                showPriorities: config.showPriorities,
                toggleCompletion: { viewModel.toggleCompletion(id: task.id) }
            )
            .contextMenu { // <7>
                Button("Eliminar tarea") {
                    viewModel.removeTask(id: task.id)
                }
            }
        }
    }

    /// Un enlace (Binding) para que el detalle edite la tarea. No toca los datos:
    /// leer y escribir se traducen a métodos del ViewModel.
    private func binding(for task: Task) -> Binding<Task> {
        Binding( // <8>
            get: { viewModel.task(id: task.id) ?? task },
            set: { viewModel.updateTask($0) }
        )
    }
}
----
<1> La pila de pantallas. La lista es la primera; el detalle se empuja encima.
<2> Cada tarea se dibuja con `taskRow(task:)`: el `body` queda corto y la fila se lee por separado.
<3> Los flags y «Añadir tarea» pasan a la barra de la ventana. El `#if Prioridades` funciona igual que en la sesión 4.
<4> El título de la lista en la barra.
<5> Cada fila es un enlace: al pulsarla, se empuja el detalle con un *binding* a *esa* tarea.
<6> La fila de la sesión 4, sin cambios. El botón de marcar sigue funcionando dentro del enlace.
<7> Clic derecho sobre la fila: «Eliminar tarea». En escritorio es la forma de borrar (`.onDelete`, el deslizar de iOS, no tiene equivalente).
<8> Un `Binding` hecho a mano: `get` pide la tarea al ViewModel y `set` le entrega la tarea editada. La vista no modifica el array: eso lo hace el ViewModel, como pide MVVM.

[NOTE]
====
SwiftUI permite escribir lo mismo con `List($viewModel.tasks) { $task in ... TaskDetailView(task: $task) }`. Es correcto, pero el compilador de Swift 6.3 para Windows falla con un error interno al usar `$task` dentro de ese cierre. `binding(for:)` hace lo mismo y compila en los tres sistemas.

=== Paso 3: probar los dos productos

No hay que tocar nada más: `TaskApp.swift` sigue creando `TaskListView()` y el detalle es un fichero nuevo dentro de la carpeta sincronizada, así que entra en los dos targets.

* *macOS:* elegid el scheme `TaskApp` o `TaskApp Prioridades` y pulsad ▶.
* *Linux y Windows:* `swift run TaskApp` o `swift run --traits Prioridades TaskApp`.

Comprobad: marcar una tarea desde la fila no abre el detalle; pulsar la fila sí; lo que se edita en el detalle aparece en la lista al volver; el clic derecho sobre una fila la borra.

Preguntas para comentar: ¿quién es el dueño de la tarea que se edita? ¿Qué pasaría si `TaskDetailView` recibiera `let task: Task` en lugar de `@Binding`? ¿Por qué no hace falta ningún `#if` para la navegación?

=== Paso 4: una rama de Git para una nueva característica

[source,shell]
----
# 1. Situarse en la rama de integración (si no existe: git switch -c develop)
git switch develop

# 2. Crear y cambiar a una rama para la característica
git switch -c feature/task-editing

# 3. Trabajar, y confirmar los cambios con un mensaje descriptivo
git add .
git commit -m "feat: add task detail view"

# 4. Volver a develop e integrar la característica
git switch develop
git merge --no-ff feature/task-editing

# 5. Ver el historial con las ramas
git log --oneline --graph
----

=== Qué hay que hacer

. *Crear la vista de detalle del libro* en `Core/Views/`, con un `Form` que permita modificar al menos el título y el estado de lectura, y que reciba el libro con `@Binding`.

  * crea una rama personal con el formato `feature/nombre-feature-tu-nombre`;

=== Comprobad vuestro diseño

* ¿Quién es el dueño del dato que se edita: el listado, el detalle o el ViewModel? ¿Qué pasaría si el detalle recibiera una *copia* del libro?
